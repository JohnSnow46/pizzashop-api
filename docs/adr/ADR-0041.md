# ADR-0041: Retry płatności PayU dla gościa — `InitializeGuestPaymentCommand` i model zaufania `GuestTrackingToken` rozszerzony na akcję inicjującą bramkę

**Data:** 2026-07-27
**Status:** Zaakceptowana

**Kontekst.**
ADR-0018 (Decyzja 3) odłożył wariant gościa dla ponowienia płatności, flagując go jawnie jako
wymagający „świadomego przeglądu bezpieczeństwa (token jako jedyny czynnik autoryzacji akcji
płatniczej)" — w odróżnieniu od `GetOrderByTrackingTokenQuery`, gdzie `GuestTrackingToken`
autoryzuje wyłącznie **odczyt** (ADR-0021, ADR-0028, ADR-0038). Ten dokument domyka ten
przegląd: `InitializeGuestPaymentCommand` będzie pierwszym miejscem, gdzie posiadanie
`GuestTrackingToken` autoryzuje **akcję z efektem ubocznym** — wywołanie zewnętrznej bramki
PayU i zapis nowej `ProviderPaymentReference`.

Właściwości `GuestTrackingToken` istotne dla tej oceny (bez zmian, ustalone wcześniej):
- generowany jako `Guid.NewGuid()` (122 bity losowości, praktycznie nieodgadnialny) —
  `CreateOrderCommandHandler`;
- unikalny indeks w bazie (ADR-0021) — brak enumeracji przez timing/kolizje;
- ten sam token już dziś trafia do przeglądarki gościa (link `/orders/track/:trackingToken`
  na `OrderConfirmationPage`) i bywa współdzielony (e-mail, historia przeglądarki, drugi
  telefon) — to istniejąca, zaakceptowana ekspozycja, nie nowa.

**Decyzja.**
`InitializeGuestPaymentCommand(GuestTrackingToken)` wywołuje dokładnie ten sam guard co
`InitializePaymentCommand` (`EnsureCanInitializePayment`: `PaymentMethod != Online` lub
`PaymentStatus == Paid` ⇒ `ConflictException`/409), bez żadnej dodatkowej ownership-owej
warstwy — analogicznie do `GetOrderByTrackingTokenQueryHandler`, posiadanie tokenu **jest**
autoryzacją. Endpoint jest `[AllowAnonymous]`.

Świadomie **nie** wprowadzamy w tej iteracji:
- **rate limitingu** (per-token/per-IP) — w projekcie nie istnieje dziś żadna infrastruktura
  rate-limitingu (sprawdzone: brak `AddRateLimiter`/middleware); dodanie jej punktowo tylko
  dla tego jednego endpointu byłoby niespójne, a dodanie jej globalnie to osobna decyzja
  wykraczająca poza zakres tego zadania (CLAUDE.md: nie projektować pod skalę enterprise bez
  wyraźnej potrzeby);
- **jednorazowości tokenu / unieważniania po użyciu** — token służy też do `GetByTrackingTokenAsync`
  (odczyt statusu) i do subskrypcji SignalR (`SubscribeToGuestOrder`, ADR-0028) przez cały
  cykl życia zamówienia; unieważnienie po jednym użyciu inicjalizacji zepsułoby te ścieżki i
  uniemożliwiło legalny scenariusz „gość klika ponów płatność drugi raz, bo pierwsza sesja
  PayU też wygasła";
- **powiązania z IP/sesją** — gość z definicji nie ma sesji/konta; wiązanie z IP jest kruche
  (NAT, sieci komórkowe, VPN) i nie podnosi realnie poprzeczki wobec kogoś, kto już ma token.

**Uzasadnienie akceptacji ryzyka.** Najgorszy scenariusz nadużycia (ktoś inny niż gość zdobył
token i wielokrotnie odpala inicjalizację) to powtarzane wywołania `IPaymentGateway.InitializePaymentAsync`
dla tego samego, wciąż nieopłaconego zamówienia — nie da się w ten sposób ukraść pieniędzy ani
zmienić stanu zamówienia poza sesją bramki (guard blokuje `Paid`/`OnPickup`), a każda kolejna
sesja PayU nadpisuje jedynie `ProviderPaymentReference` (idempotentny refund per ADR-0018 i tak
operuje na ostatniej referencji). Konsekwencja to najwyżej uciążliwość (dodatkowe, nieużyte
sesje w PayU), nie utrata danych/pieniędzy ani przejęcie konta — akceptowalne dla projektu
portfolio w skali jednej pizzerii.

**Konsekwencje.**
- Nowy `ConflictException`/`NotFoundException` z tego handlera mają identyczną semantykę HTTP
  jak w wariancie zalogowanym (409/404) — spójne dla frontendu niezależnie od tego, którym
  klientem API woła.
- Jeśli w przyszłości pojawi się realny sygnał nadużycia (np. logi pokażą powtarzane wywołania
  z jednego tokenu w krótkim czasie), właściwym follow-upem jest **globalny** rate-limiting w
  Api (np. ASP.NET Core `Microsoft.AspNetCore.RateLimiting`) obejmujący wszystkie endpointy
  `[AllowAnonymous]` operujące na tokenie (`GetByTrackingToken`, `InitializeGuestPayment`,
  Hub `SubscribeToGuestOrder`), nie punktowa łatka na jednym endpoincie — nowy ADR w razie
  potrzeby.
- `EnsureCanInitializePayment` zostaje wydzielony do współdzielonej klasy
  (`internal static PaymentInitializationGuard`, namespace `Payments.Commands`) używanej przez
  `InitializePaymentCommandHandler` i `InitializeGuestPaymentCommandHandler` — czysto
  mechaniczne przeniesienie (bez zmiany logiki/komunikatów wyjątków), konieczne żeby nie
  duplikować identycznej reguły stanu w dwóch handlerach.
- ADR-0018 Decyzja 3 pozostaje aktualna w części „kształt komendy"; ten ADR domyka wyłącznie
  odłożoną część „przegląd bezpieczeństwa".
