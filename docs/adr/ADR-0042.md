# ADR-0042: Oceny i recenzje pozycji menu (nowy agregat `Review`)

**Data:** 2026-09-28
**Status:** Zaakceptowana

**Kontekst.**
`docs/roadmap.md` poz. 5: repo dziś w ogóle nie ma ocen/recenzji — typowej funkcji e-commerce,
brakującej w portfolio pokazującym pełny cykl zakupowy. Klient, który odebrał zamówienie,
powinien móc ocenić (1-5) i opcjonalnie skomentować konkretną pozycję menu z tego zamówienia.

Roadmapa mówi "tylko dla zamówień w statusie Delivered" — w rzeczywistym `OrderStatus`
(domain-model.md 5.3) nie ma stanu `Delivered`; stanem końcowym dostarczenia/odbioru jest
`Completed` (`OutForDelivery → Completed` dla Delivery, `Ready → Completed` dla Pickup).
Ta decyzja koryguje roadmapę: warunkiem recenzowalności jest `Order.Status == Completed`.

Pytania rozstrzygnięte tym ADR (nieoczywiste z samej roadmapy):
1. Czy goście (zamówienia bez `CustomerId`) mogą wystawiać recenzje?
2. Co dokładnie oznacza "jedna recenzja na pozycję" — per `OrderItem` (linia zamówienia,
   z wariantem) czy per `MenuItemId` w danym zamówieniu?
3. Gdzie żyje reguła "tylko własne, dostarczone zamówienie" — w `Review` (Domain), czy jako
   koordynacja Application między dwoma agregatami?

**Decyzja.**

*(A) Tylko zarejestrowani klienci.* Recenzja wymaga `CustomerId` (nie `null`). Uzasadnienie:
recenzja to trwała, publiczna treść przypisana do tożsamości — dopuszczenie gości otwierałoby
pytania o moderację/spam bez mechanizmu identyfikacji, którego to repo świadomie nie ma
(brak kont gościa, ADR-0005). Jeśli w przyszłości pojawi się potrzeba recenzji gości, to
osobna decyzja (inny model zaufania), nie rozszerzenie tego ADR.

*(B) Jedna recenzja per (`OrderId`, `MenuItemId`)*, nie per `OrderItem`/wariant. Klient
recenzuje "Margheritę z tego zamówienia", nie osobno każdy wariant/dodatek tej samej pozycji
menu w obrębie jednego zamówienia — prostsze UX, zgodne z tym, jak recenzje pozycji menu
działają w praktyce (recenzja dotyczy produktu z katalogu, nie konkretnej konfiguracji).
Wymuszone unikalnym indeksem DB na `(OrderId, MenuItemId)`.

*(C) Nowy, mały agregat `Review`** (Domain/Reviews), odsprzężony od `Order`/`MenuItem`**
(żadnych referencji obiektowych, tylko `Guid` — ten sam wzorzec co `Promotion`/
`OrderDiscountContext`, ADR-0011). Własne niezmienniki Domain (guard clauses w `Create`):
- `OrderId`, `CustomerId`, `MenuItemId` — wymagane (`!= Guid.Empty`).
- `Rating` — całkowita liczba **1-5** (`ArgumentOutOfRangeException` poza zakresem).
- `Comment` — opcjonalny; jeśli podany, po `Trim()` niepusty i **≤ 1000 znaków**
  (`ArgumentException`) — analogiczny bound do innych pól tekstowych w repo (np. `Order`
  notes), zapobiega nadużyciom bez sztucznego ograniczania treściwej recenzji.
- `CreatedAt` (`DateTimeOffset`) — ustawiane przez wywołującego (Application, przez `IClock`),
  nie `DateTimeOffset.UtcNow` bezpośrednio w Domain (spójne z resztą repo).

*(D) Uprawnienie do wystawienia recenzji — koordynacja w Application, NIE w Domain.*
`Review` (Domain) nie zna `Order` ani jego statusu — sprawdzenie "to zamówienie należy do
Ciebie, jest `Completed`, i zawiera tę pozycję menu" wymaga odczytu **innego** agregatu
(`Order`), więc zgodnie z ustalonym wzorcem repo (CLAUDE.md "Reguły biznesowe zależne od
stanu... guard clauses w Domain" dotyczy reguł **wewnątrz jednego agregatu**; reguły
**między** agregatami już dziś żyją w handlerach Application — por. `RecordUsage`+
`Order.AppliedPromotionId` w tym samym handlerze) — mapowanie na istniejące wyjątki
Application (ADR-0017/ADR-0018), bez nowych typów:
- Zamówienie nie istnieje / nie należy do bieżącego klienta → `NotFoundException`
  (ADR-0017 wzorzec: nieujawnianie cudzego zamówienia przez 403 vs 404 — tu 404, spójnie z
  `GetOrderByIdQuery`, żeby nie ujawniać istnienia cudzego zamówienia).
- Zamówienie istnieje, należy do klienta, ale `Status != Completed` → `ConflictException`
  ("Order is not yet completed.").
- `MenuItemId` nie występuje wśród `Order.Items` → `ConflictException`
  ("This menu item was not part of the order.").
- Recenzja dla tej pary `(OrderId, MenuItemId)` już istnieje → `ConflictException`
  ("This item has already been reviewed.") — sprawdzone przez handler (odczyt przed
  zapisem) I wymuszone unikalnym indeksem DB jako druga linia obrony (wyścig współbieżnych
  requestów).

*(E) Odczyt — dwa niezależne widoki, bez paginacji* (spójnie z ADR-0039 — skala tego repo:
jedna pizzeria, realistycznie dziesiątki-setki recenzji na pozycję menu):
- `GET /api/menu-items/{id}/reviews` — publiczny (`AllowAnonymous`), lista recenzji danej
  pozycji + średnia ocena, do wyświetlenia w katalogu.
- `GET /api/reviews/mine` — `[Authorize(Roles=Customer)]`, własne recenzje (do UI "czy już
  oceniłem tę pozycję").

**Konsekwencje.**
- Nowy agregat: `src/PizzaShop.Domain/Reviews/Review.cs`.
- Nowa tabela `Reviews`, unikalny indeks `(OrderId, MenuItemId)`, EF Core migracja.
- Nowy port `IReviewRepository` (Application/Abstractions/Persistence) + implementacja EF
  (Infrastructure/Persistence/Repositories).
- Nowy moduł `Application/Reviews` (Commands/`CreateReviewCommand`, Queries/
  `GetMenuItemReviewsQuery` + `GetMyReviewsQuery`, Dtos, Validators) — wzorzec 1:1 z
  `Application/Promotions`.
- Nowy `ReviewsController` (Api) — `POST /api/reviews` (Customer), `GET
  /api/menu-items/{id}/reviews` (anonim), `GET /api/reviews/mine` (Customer).
- Zero zmian w `Order`/`MenuItem`/`Promotion` (Domain) — `Review` jest czysto addytywny,
  referencje tylko przez `Guid`.
- Świadomie POZA zakresem: edycja/usuwanie recenzji, moderacja/zgłaszanie nadużyć,
  odpowiedź restauracji na recenzję, wpływ recenzji na wyszukiwanie/sortowanie katalogu,
  recenzje gości (patrz A) — każde jako osobna, przyszła decyzja jeśli będzie potrzebna.

**Zakres dla buildera.**
1. `src/PizzaShop.Domain/Reviews/Review.cs` — agregat, prywatny konstruktor (EF, ADR-0020),
   `Create(orderId, customerId, menuItemId, rating, comment, createdAt)` z guardami wyżej.
2. `src/PizzaShop.Domain/Exceptions/` — **brak nowych** typów (guardy Domain używają
   `ArgumentException`/`ArgumentOutOfRangeException`, spójnie z `LoyaltyAccount`/`Money`).
3. `src/PizzaShop.Application/Abstractions/Persistence/IReviewRepository.cs` —
   `GetByOrderAndMenuItemAsync(orderId, menuItemId, ct)`, `GetByMenuItemIdAsync(menuItemId, ct)`,
   `GetByCustomerIdAsync(customerId, ct)`, `AddAsync(review, ct)`.
4. `src/PizzaShop.Infrastructure/Persistence/Repositories/ReviewRepository.cs` — implementacja EF.
5. `src/PizzaShop.Infrastructure/Persistence/Configurations/ReviewConfiguration.cs` —
   `HasIndex(r => new { r.OrderId, r.MenuItemId }).IsUnique()`, `Comment` `HasMaxLength(1000)`.
6. `PizzaShopDbContext.cs` — `DbSet<Review> Reviews => Set<Review>();`.
7. EF Core migracja (`dotnet ef migrations add AddReviews ...`).
8. `Application/Reviews/Commands/CreateReviewCommand.cs` (+Handler+Validator) — handler robi
   (D) w tej kolejności: `_orderRepository.GetByIdAsync` → ownership+status+item-membership →
   `_reviewRepository.GetByOrderAndMenuItemAsync` (duplicate check) → `Review.Create` →
   `AddAsync` → `IUnitOfWork.SaveChangesAsync`. Walidator FluentValidation sprawdza tylko
   kształt (Rating 1-5, Comment ≤1000) — reguły (D) w handlerze, nie walidatorze (są
   zależne od stanu innego agregatu, nie kształtu wejścia).
9. `Application/Reviews/Queries/GetMenuItemReviewsQuery.cs` (+Handler) — bez auth, zwraca
   `IReadOnlyList<ReviewDto>` + `AverageRating` (osobny DTO `MenuItemReviewsDto` albo
   dwa pola — decyzja buildera, byle jedna zwięzła odpowiedź).
10. `Application/Reviews/Queries/GetMyReviewsQuery.cs` (+Handler) — wzorzec jak
    `GetMyOrdersQueryHandler` (ADR-0039): `ICurrentUser.CustomerId`, `ForbiddenOperationException`
    gdy null (defensywnie, mimo że route wymusza rolę).
11. `Application/Reviews/Dtos/ReviewDto.cs` + `ReviewMapper.cs`.
12. `src/PizzaShop.Api/Controllers/ReviewsController.cs` — trzy endpointy jak w (E)+(D).
13. `Infrastructure/DependencyInjection.cs` — `services.AddScoped<IReviewRepository, ReviewRepository>();`.
14. Testy (xUnit+Moq/FluentAssertions): `ReviewTests` (guardy Domain — rating poza [1,5],
    pusty/za długi comment, puste guidy), `CreateReviewCommandHandlerTests` (happy path,
    cudze zamówienie → NotFound, niedostarczone → Conflict, pozycja spoza zamówienia →
    Conflict, duplikat → Conflict), `CreateReviewCommandValidatorTests`,
    `GetMenuItemReviewsQueryHandlerTests` (średnia, pusta lista), `GetMyReviewsQueryHandlerTests`.
15. Frontend — **poza zakresem tego ADR** (backend-first, spójnie z tym jak ADR-0039 rozdzielił
    backend od frontendu w osobnym zadaniu).

**Nie w zakresie tego ADR:** edycja/usuwanie recenzji, moderacja, odpowiedzi restauracji,
wpływ na sortowanie katalogu, recenzje gości, frontend.
